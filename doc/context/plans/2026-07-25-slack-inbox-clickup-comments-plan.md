## Design

### A. Slack inbox read (new stage in `run-hourly.sh`, runs BEFORE the feed gather loop)

Colocated `read-slack-inbox.sh` (skill dir):
1. A pinned-haiku `claude -p` micro-call in the `pl_post_slack` shape (`--allowedTools "mcp__claude_ai_Slack_Bot__mintRestBearerForCurl"`, `--permission-mode dontAsk`, 120s watchdog, `CLAUDE_HISTORY_ROLE=0`) that outputs ONLY the bearer token + base URL.
2. Bash `curl`s the **verified proxy endpoint above** (oldest = scan floor, `limit=100`, following `nextCursor` **until `hasMore=false`**, safety ceiling 20 pages) into `tmp/gather-inbox/<ts>/messages.json`. Hitting the ceiling with `hasMore` still true = inbox stage error (no watermark advance — older unread messages must never be skipped below a max-scanned watermark). The bearer lives in a shell variable only — never logged, never written to disk; 5-min TTL is ample (reads happen immediately).
   **Scan floor = `last_ts − 3 days`** (never below the seed), not `last_ts`: Slack messages keep their original `ts` when edited, so a recently processed message that Peter later edits to add a link is re-scanned; already-accounted links are dropped by URL-level dedup (below), so the overlap costs nothing. (Peter's own example message carries an `edited` stamp — this case is real.)
3. Every `curl` carries `--connect-timeout 10 -m 30`; the **whole inbox stage (read + gather-inbox)** runs under a driver-level `pl_spawn_killer` watchdog (`INBOX_WATCHDOG_SECS`, default 360; the mjs soft deadline sits below it) — a hung proxy or browser must never eat the feed stage's window.
4. Any failure or timeout (mint, curl, invalid JSON, watchdog kill) → inbox stage skipped this fire, ⚠️ bookend note, watermark untouched (messages retried next fire). Never blocks the feed flow.

### B. `fast/gather-inbox.mjs` (new, colocated with `gather-feed.mjs`)

Deterministic node script. Input: `--messages-file`, `--state-file`, `--out-dir`, `--deadline-secs`, `--max-links` (default 5), `--comments-file`. Shares the exact key helpers with the feed gather: `authorSlug`/`normText`/`makeKey`/`fuzzyId` move to a tiny `fast/keys.mjs` imported by BOTH scripts (pure string functions — the only refactor of `gather-feed.mjs`).

1. **Message selection**: all messages in the scan window, sorted **oldest-first**; keep if `bot_id` absent AND `user` present; allow `subtype` null / `file_share` / `thread_broadcast`; skip joins/system subtypes. Top-level channel messages only (thread replies NOT scanned — deliberate, see Out of scope).
2. **Link extraction** per message: from `text` (`<url|label>` unwrapping), `attachments[].from_url|original_url`, and `blocks[]` rich-text link elements; union. LinkedIn post link forms accepted as input: `linkedin.com/posts/<slug>`, `lnkd.in/<code>`, `linkedin.com/feed/update/<urn>`. Tracking queries stripped; every URL reduced to a **normalized identity form** (origin+path, no query/fragment, trailing slash trimmed). Non-LinkedIn links ignored; messages with no LinkedIn links just advance the watermark.
3. **Work queue** (identity = normalized URL): coalesce `state.pending` ∪ new links across ALL messages — one queue item per normalized URL with a `requests[]` provenance list (`{message_ts, user}` per mention, merged on duplicates). Links already **accounted** are dropped: normalized-URL match against ledger `post_url`s, `state.pending`, or `state.dead` — this is also what makes the edited-message overlap window free. A dead URL mentioned in a **new** message (`ts > last_ts`) is *revived* to pending (explicit re-request beats a dead-letter verdict); window-replayed old messages never revive dead links. Fetch order: pending retries first (oldest), then new; capped at `--max-links` — overflow stays in `pending` (durable backlog — nothing is lost to the cap; bookend reports backlog size).
4. **Dedup (disposition-aware)** against `comments.json` (by canonical URL match pre-fetch, then key + fuzzyId post-fetch):
   - matched `drafted` → no re-draft; emitted in the contract as `POST_<i>_MODE=clickup-only` if the entry lacks `clickup_task_id` (ClickUp delivery still owed), else counted `INBOX_DUPLICATES`.
   - matched `off-topic` → **fully reprocessed** (Peter explicitly curated it; the earlier verdict was the automated filter's) — contract mode `reprocess-off-topic`; the drafting step updates the existing entry in place (disposition → drafted).
   - matched `already-commented` → skipped, counted, noted (Peter already commented there).
5. **Fetch** each remaining link in the persistent-profile browser (own `launchBrowser` copy of the feed gather's launch/lock/auth error mapping): navigate, expand "…see more" and **assert the expansion took** (no residual `…more` truncation marker on the scraped body), scrape author name, author profile URL, headline, full body from the post detail page. After fetch, coalesce by `key` — two input URLs resolving to the same post yield ONE contract entry with merged `requests[]`. Failure policy: a page **positively identified** as gone dead-letters immediately — matched by a dedicated `TOMBSTONE_RE` (deleted / removed / no longer available / page not found), deliberately NARROWER than the feed's `RENDER_ERROR_RE`, whose "Something went wrong" / "couldn't be loaded" phrases are transient load errors, not evidence of deletion; all other failures (nav timeout, generic error, incomplete expansion) keep the link in `state.pending` with `attempts+1` + `last_error`, retried on later fires; at `attempts ≥ 5` it moves to `state.dead` and the bookend names the URL + reason (an actionable alert — Peter re-drops the link to revive it). Nothing is ever silently discarded.
6. **Canonical permalink**: final page URL when it is `/posts/<slug>` (query stripped; the natural case for `/posts/` and `lnkd.in` inputs). Fallback trust classes mirror the feed gather: a `/posts/` input whose page couldn't be positively verified keeps the stripped input URL; an `lnkd.in` input keeps the short link (both counted `PERMALINKS_UNVERIFIED`) — so inbox posts from `/posts/`/`lnkd.in` inputs ALWAYS carry a link. `/feed/update/` inputs whose final URL never reaches `/posts/`: try the post page's control-menu copy-link recovery; if still no `/posts/` URL the link is NOT delivered linkless — it stays pending per the failure policy above (never emit `/feed/update/`; the ClickUp deliverable explicitly includes the link).
7. **Contract** (`contract.env`, same `POST_<i>_*` shape + body files): adds `INBOX_MSGS_SCANNED`, `INBOX_MSGS_HUMAN`, `INBOX_LINKS_FOUND`, `INBOX_DUPLICATES`, `INBOX_SKIPPED_ALREADY_COMMENTED`, `INBOX_FETCH_FAILED`, `INBOX_BACKLOG` (pending size after this run), `INBOX_DEAD` (total dead), `PERMALINKS_UNVERIFIED`, `PROPOSED_WATERMARK` (= exact max message ts in the captured snapshot — safe because every extracted link is conserved into the contract, `pending`, `dead`, or an accounted-dedup), `PROPOSED_STATE_FILE` (path to the *proposed* new state JSON written under the out-dir), and per-post `POST_<i>_SOURCE=slack-inbox`, `POST_<i>_SOURCE_TS`, `POST_<i>_SOURCE_USER`, `POST_<i>_REQUESTS` (JSON list), `POST_<i>_MODE=draft|clickup-only|reprocess-off-topic`, `POST_<i>_MATCHED_KEY` (the exact ledger key when dedup matched an existing entry to update in place). A `manifest.json` records the **link-conservation transition**, accounted at the **job** level (job = normalized URL after alias merging; every job resolves to exactly ONE bucket — contract row, pending, dead, or accounted-dedup — with alias URLs and `requests[]` merged into their job, and pre-fetch ledger matches grouped by matched ledger key exactly like post-fetch key coalescing, so a canonical-URL + short-link alias pair can neither emit duplicate rows nor unbalance the equation): `jobs = contract_posts + pending_out_new + dead_new + accounted_dupes + skipped_already_commented` — the driver re-checks this arithmetic.
8. Exit codes: 0 ok / 10 partial / 20 auth / 21 profile-locked / 22 rate-limited / 23 fs. No interest classification, no repost filter (Peter curated the links himself).

### C. Watermark + state — `linkedin-compain/slack-inbox.json` (new, git-tracked)

```json
{ "last_ts": "1784992000.000000", "updated_at": "<iso>",
  "pending": [ {"url":"…","message_ts":"…","user":"…","attempts":1,"last_error":"…","first_seen":"<iso>"} ],
  "dead":    [ {"url":"…","message_ts":"…","reason":"…","died_at":"<iso>"} ] }
```
- **Seeded at implementation time** with `last_ts = 1784992000.000000` (the documented deployment cutoff — just before Peter's example message, so it is the first message ever processed). No "default lookback window" guessing.
- `gather-inbox.mjs` only **reads** the tracked file and writes a *proposed* successor under its out-dir. `run-hourly.sh` installs the proposed state (`jq`-validated) **only after the drafting phase exits 0 AND a deterministic postcondition check passes**: for every inbox contract row, `jq` confirms `comments.json` now holds an entry at that key (`reprocess-off-topic` rows additionally at disposition `drafted`) — a session that "succeeded" while silently skipping a post must not consume its message. Any missing key → old state retained, ⚠️ inbox-delivery failure noted. (When the inbox found no posts, the state installs directly.) A failed/killed drafting run leaves the watermark untouched → next fire rescans the same messages; `comments.json` dedup absorbs the already-drafted subset. Nothing advances past undelivered work.
- Post-deploy, a **missing or corrupt** state file is an inbox-stage error (skip inbox, ⚠️ note, no advance) — never guess a window.
- The state file lands in the same `linkedin-compain/` data commit as `comments.json` (auto-merged even on healed fires — the split-landing `git add linkedin-compain` already covers it).

### D. Same-fire cross-source dedup

Inbox gather runs FIRST. Its contract dir includes `keys.json` (`[{key, fuzzy}]` of every accepted inbox post). `gather-feed.mjs` gains `--extra-seen-file=<path>`: entries loaded into its existing seen/fuzzy sets, so a post arriving via both Slack and the feed in the same fire is accepted once (inbox wins; feed counts it as already-seen). Minimal diff to the battle-tested feed scraper: one optional file read into existing structures.

### E. Drafting phase changes (SKILL.md + orchestration)

- `run-hourly.sh` passes BOTH contract paths: "using the pre-gathered contracts at <feed>/contract.env and <inbox>/contract.env".
- The skill processes the union; prep-refs once; draft agents fan out in one parallel message over every `MODE=draft|reprocess-off-topic` post; sequential write+Slack+ClickUp loop covers all posts.
- Per post in the sequential loop (Step 2b), in this order (ledger-first, so a kill at any point leaves a durable record for reconciliation):
  1. **`comments.json` append** (or in-place update at `POST_<i>_MATCHED_KEY` for `reprocess-off-topic` / `clickup-only` modes) via `jq`, with `clickup_task_id: null`.
  2. **ClickUp task create, search-first**: once per fire the session fetches the list's existing tasks (`listTasks`, paginated, `includeClosed=true` — the list is small). **Adoption identity is the embedded key or the exact normalized Source/post URL only** — the deterministic name (`<author_name> — <first ~60 chars>`) merely narrows candidates, whose descriptions are then read (`getTask`) to check for `_key: <key>_`; two posts by one author with the same opening must never share a task. If the exhaustive lookup itself fails, **fail closed**: create nothing, record `clickup_error`, leave the entry reconcilable — never risk a duplicate behind a broken search. On a confirmed miss, `mcp__claude_ai_ClickUP__createTask` on `901524736848`; the post `key` is embedded in the **initial** task description footer (`_key: <key>_` — identity travels in the create call, not a later best-effort field write); then `setCustomFieldValue` Source = post_url (best-effort). Update the entry's `clickup_task_id`/`clickup_url` (or `clickup_error`).
  3. Slack summary + thread (post text + variants) — `draft`/`reprocess` modes only.
- **Any accepted post whose draft agent failed — feed and inbox alike**: still gets steps 1–2 (entry with disposition `drafted`, empty `variants`, `slack_error` noting the draft failure; ClickUp task with the post). The report + bookend name these posts explicitly — the ClickUp task carries the full post, so Peter can rerun `linkedin-comment-ideas` on it by hand. No automated draft-retry machinery (failure is rare and now always visible + recoverable; a delivery-state machine is not warranted at this scale).
- **ClickUp reconciliation sub-step**: criterion = post-feature entry (`source` set) with `clickup_task_id == null`, regardless of `clickup_error` — up to 5 per fire, oldest first, search-first as above. Runs in the drafting session when one exists; when NO drafting session would run, the driver computes the reconcilable count itself (`jq`) and, if > 0, spawns a minimal reconcile-only `claude -p` (same skill, "reconcile only" prompt) so missing tasks can't strand forever behind quiet fires.
- Drafting runs when `feed_posts + inbox_posts > 0`. If the feed loop ends `fail` on exits 20/22 or heal-abort but the inbox contract is valid with posts, drafting still runs **inbox-only** (the fire still exits red for the feed failure). Exit 31 (classifier/`claude -p` dead) skips drafting entirely — the drafting session runs on the same `claude -p`.
- Selector-drift fallback (exit 30): legacy agent gathers the feed; the inbox contract (already produced) is passed alongside — inbox posts are never held hostage by feed DOM drift. Because the legacy agent can't read `--extra-seen-file`, the SKILL's Step 2b opens with a **cross-source dedup gate**: before processing any feed post, its key/fuzzy id is checked against the inbox contract's `keys.json`; matches are skipped (inbox wins) — so same-fire duplicates are impossible on the fallback path too.
- `comments.json` entries gain optional fields: `source` (`"feed"` | `"slack-inbox"`; legacy entries lack it), `slack_request_ts`, `slack_request_user`, `clickup_task_id`, `clickup_url`, `clickup_error`. CLAUDE.md ledger description updated accordingly.

## Out of scope (deliberate — with reasons)

- **Edits older than the 3-day overlap horizon are not seen.** Slack keeps a message's original `ts` on edit, and this design polls history rather than consuming edit events; a link added by editing a message >3 days past the watermark will not be picked up. Explicit, documented limitation (full edit-event tracking or unbounded content-hash rescans are not warranted for this channel's traffic); re-dropping the link in a fresh message always works.
- **Feed-gather acceptance semantics are unchanged.** A feed post that today ships to Slack with a missing permalink (`PERMALINKS_MISSING`, already an error + post-landing heal) or a twice-failed see-more body gets its ClickUp task with exactly what Slack gets — the ClickUp mirror deliberately tracks Slack delivery rather than forking the battle-tested feed acceptance rules. Hardened completeness (expansion assert, always-linked) applies to the NEW inbox path only.
- **Thread replies are not scanned.** Peter's example and stated flow are top-level channel messages; the channel's threads are overwhelmingly bot-authored draft threads, and scanning every thread since the watermark multiplies API calls for a flow that has no observed use. Documented limitation; revisit on request.
- **No comment variants in ClickUp** (Peter's explicit choice).
- **No backfill** of ClickUp tasks for pre-feature drafted entries (reconciliation only covers post-feature entries; backfill on request).
- **No interest/repost filtering for inbox links** (human-curated).
- **The legacy gather-feed fallback agent is not taught about the inbox** — the inbox path is deterministic and independent; it doesn't share the feed's selector-drift failure mode.
- **Inbox failures don't heal in v1** — durable backlog + ⚠️ visibility instead; the heal budget stays reserved for the feed gather that must ship every morning.
- **No per-post delivery-state machine / automated draft or Slack retries.** Draft/Slack failures are rare, now always leave a durable ledger record + ClickUp task, and are named in the report — visibility + a one-command manual rerun beats a retry state machine at this scale.
- **No fire-blocking when a previous fire's data failed to land.** A replay after a failed data landing can duplicate Slack drafts (an existing, accepted pipeline characteristic — rare path); ClickUp duplication specifically is prevented by search-first create. Wedging the morning pipeline on unresolved state would be worse than the rare duplicate.
- **No verify-and-repair of ClickUp tasks that already have an id** — nothing else edits those tasks; reconciliation covers absence, not drift.
